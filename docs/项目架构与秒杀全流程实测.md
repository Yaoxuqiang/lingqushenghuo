# hm-dianping 项目架构分析与秒杀全流程实测

> 代码基线：`E:\heimadianping_code_yuerufeng\hm-dianping`
> 实测时间：2026-09-28 · 实测环境：JDK 11 + MySQL 8.0(3306) + Redis 3.2(6379) + 无 Kafka

---

## 0. 一句话结论

这是一个**单模块 Spring Boot 本地生活服务后端**，9 个 Controller、11 组 Service、10 个 Mapper，所有"高并发味道"的技术点都压在**秒杀优惠券**这一条链路上：Redis Lua 原子校验 → 消息队列异步下单 → Redisson 分布式锁 → MySQL 行级扣减。

**实测发现：整条链路是"半通"的。** Redis 侧完全正常（库存扣减、一人一单都生效），但消息队列的消费端被注释掉了，本机也没有 Kafka，所以**订单永远不会落库**。

## 4. 亮点（按面试价值排序）

### 亮点 1：Lua 把"校验 + 扣减"压成一次原子操作

`resources/seckill.lua` 在 Redis 单线程里一次性完成三件事，中间不可能被别的请求插队：

```lua
if(tonumber(redis.call('get', stockKey)) <= 0) then return 1 end   -- 库存不足
if(redis.call('sismember', orderKey, userId) == 1) then return 2 end -- 重复下单
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
return 0
```

**为什么好**：如果这三步写成 Java 代码，就必须加分布式锁，或者用 `SETNX` 做"库存预占"，性能和代码量都更差。放到 Lua 里，Redis 保证了脚本执行的原子性 —— 相当于把"查库存、查重、扣减"打包成一个不可分割的动作。

### 亮点 2：三种缓存问题各有一套方案，而且并存可切换

`utils/CacheClient.java` 里同时保留了三条完整实现：

| 方法 | 解决的问题 | 手段 |
|---|---|---|
| `queryWithPassThrough` | 缓存穿透 | 查不到就写空串 `""` 进 Redis，TTL 2 分钟 |
| `queryWithMutex` | 缓存击穿 | 抢 `lock:shop:{id}`，抢不到睡 50ms 递归重试 |
| `queryWithLogicalExpire` | 缓存击穿（不阻塞） | 值里包一层 `RedisData` 带 `expireTime`，过期后**先返回旧值**，后台线程异步重建 |

**为什么好**：三种方案的取舍关系一目了然，面试时可以直接对比"互斥锁会阻塞线程但保证强一致，逻辑过期不阻塞但有短暂脏数据"。

### 亮点 3：多级缓存的"可降级"设计

`VoucherListCacheService.getVoucherByShopId()` 用配置项 `hmdp.cache.voucher-list.mode` 决定走哪一层：

```java
switch (mode.toLowerCase(Locale.ROOT)) {
    case "mysql":    return loadFromDb(shopId);              // 压测基线
    case "redis":    return loadFromRedisThenDb(shopId);     // 只开 L2
    case "caffeine": default: return voucherListCache.get(shopId); // L1+L2+DB
}
```

配合 `VoucherCacheProperties`（`refreshAfterWrite=5s` / `expireAfterWrite=10m` / `redisTtl=30m`）全部外置到 `application.yaml`。

**为什么好**：这等于把"加缓存"变成了一个可以 A/B 对比的实验开关 —— 切 `mysql` 拿基线 QPS，切 `caffeine` 拿优化后 QPS，压测数据天然可复现。

### 亮点 4：滑动窗口限流做成注解

`limiter` 包三个文件构成完整闭环，调用方只写一行注解：

```java
@RateLimiter(key = "coupon:seckill:", window = 5, limit = 5,
             message = "查询次数过多，请稍后再试", type = RateLimiter.LimitType.METHOD)
@GetMapping("/of/type")
public Result queryShopByType(...)
```

底层是 `limiter.lua`：`ZREMRANGEBYSCORE` 清窗口外记录 → `ZCARD` 数当前窗口 → 未超限则 `ZADD` 以毫秒时间戳为 score。支持 `IP / USER / METHOD` 三种维度。

**为什么好**：对比固定窗口计数器，滑动窗口不会出现"窗口边界双倍流量"的问题；用 ZSet 实现比令牌桶更容易理解，且天然支持"统计最近 N 秒"这种语义。

### 亮点 5：全局唯一订单 ID（无中心化发号器）

`RedisIdWorker`：`timestamp << 32 | 自增序列`，自增序列来自 `INCR icr:order:yyyy:MM:dd`（按天分 key）。

**为什么好**：64 位里高 32 位是秒级时间戳（相对 2022-01-01 的偏移），低位是当天序号。既保证趋势递增（对 MySQL 聚簇索引友好），又不用引入雪花算法的机器号管理。

### 亮点 6：GEO + 滚动分页两个"非典型"用法

- `ShopServiceImpl.queryShopByType` 用 `GEOSEARCH ... BYRADIUS 5000 WITHDISTANCE LIMIT end`，再按距离倒序取 ID，最后 `ORDER BY FIELD(id, ...)` 保持 Redis 给出的顺序 —— 解决"Redis 分页后 MySQL 查回来顺序乱掉"的经典问题。
- `BlogServiceImpl.queryBlogOfFollow` 用 ZSet 的 score（时间戳）做游标，返回 `minTime` + `offset` 两个值处理"同一时间戳多条记录"的边界 —— 比传统 `LIMIT offset, size` 分页在 Feed 流场景下更稳（新数据插入不会导致翻页重复）。

## 5. 一条请求跑通全流程（实测）

**选的请求**：`POST /voucher-order/seckill/10`（秒杀 ID=10 的优惠券）
**为什么选它**：它是唯一一条同时穿过 *拦截器 → Controller → Lua → Redis → MQ → 消费者 → 分布式锁 → MySQL* 全链路的请求。

### 5.1 前置准备（实测命令）

```bash
# 1. 启动 Redis（项目要求密码 123456）
cd /e/Redis && ./redis-server.exe ./redis.windows.conf

# 2. 用 JDK 11 启动应用（默认端口 8081）
export JAVA_HOME="E:/jdk11/jdk-11.0.28"
mvn spring-boot:run -Dspring-boot.run.arguments=--server.port=8081

# 3. 预热秒杀库存（项目代码里没有这段逻辑，必须手工刷）
redis-cli -a 123456 set seckill:stock:10 98

# 4. 登录取 token
curl -X POST "http://localhost:8081/user/code?phone=13686869696"
curl -X POST "http://localhost:8081/user/login" -H "Content-Type: application/json" \
     -d '{"phone":"13686869696","code":"<Redis里的验证码>"}'

# 5. 发起秒杀
curl -X POST "http://localhost:8081/voucher-order/seckill/10" -H "authorization: <token>"
```

### 5.2 全链路 10 步拆解

| 步 | 环节 | 代码位置 | 做什么 | 本次实测结果 |
|---|---|---|---|---|
| 1 | Tomcat 收请求 | `VoucherOrderController:28` | `@PostMapping("seckill/{id}")` | OK |
| 2 | 刷新 token 拦截器 | `RefreshTokenInterceptor:26-46` | 从 `authorization` 头取 token → 读 `login:token:{token}` Hash → 塞进 ThreadLocal → 续期 | OK，`/user/me` 返回 `{"id":1,"nickName":"小鱼同学"}` |
| 3 | 登录校验拦截器 | `LoginInterceptor:11-20` | ThreadLocal 没用户就返回 401 | OK，不带 token 访问 `/user/me` → **HTTP 401** |
| 4 | 生成订单号 | `RedisIdWorker:27-41` | `INCR icr:order:2026:09:28` + 时间戳左移 32 位 | OK |
| 5 | 执行 Lua | `seckill.lua:17-29` | 库存判断 → 一人一单判断 → `incrby -1` → `sadd` | OK，`stock:10` 98 → **97**，`order:10` 出现成员 `1` |
| 6 | 判断 Lua 返回值 | `VoucherOrderServiceImpl:65-72` | 1=库存不足，2=重复下单 | OK，第二次请求立即返回 `{"success":false,"errorMsg":"重复下单"}`，库存仍是 97 |
| 7 | 发 MQ 消息 | `VoucherOrderServiceImpl:80` | `kafkaTemplate.send("seckill-voucher-order", order.toString())` | **阻塞**：日志疯狂刷 `Connection to node -1 (localhost/127.0.0.1:9092) could not be established` |
| 8 | 消费消息 | `SeckillVoucherConsumer:26-30` | `@KafkaListener` 被 `/* */` 注释掉了 | **未执行** |
| 9 | Redisson 加锁 | `VoucherOrderServiceImpl:90-98` | `redissonClient.getLock("lock:order:" + userId)` | **未执行** |
| 10 | 扣库存 + 落单 | `VoucherOrderServiceImpl:102-112` | `update stock-1` + `save(voucherOrder)` | **未执行**，`tb_voucher_order` 行数始终是 **3** |

### 5.3 实测证据

```
# 请求侧（12 秒超时，无响应体）
$ curl -s --max-time 12 -X POST http://localhost:8081/voucher-order/seckill/10 -H "authorization: $TOKEN"
(空)

# Redis 侧：Lua 的两件事都成功了
seckill:stock:10 = 97
seckill:order:10 = {1}

# MySQL 侧：订单没有增加
SELECT COUNT(*) FROM hmdp.tb_voucher_order;  -- 3（跑之前也是 3）

# 应用日志
```

### 5.4 对照：一条完全跑通的读链路

同一次会话里，`GET /shop/1` 是**端到端成功**的，可以直接看到缓存的"从无到有"：

```
请求前 cache:shop:1 是否存在 = 0
GET /shop/1 → {"success":true,"data":{"id":1,"name":"1000茶餐厅",...}}
请求后 cache:shop:1 是否存在 = 1
缓存内容 = {"area":"大关","openHours":"10:00-22:00","sold":4215,...}
TTL = 1798 秒（CACHE_SHOP_TTL = 30 分钟）
```

这条链路证明了 `CacheClient.queryWithPassThrough` 的"穿透 → 回源 → 回写"三步是正常的。

## 6. 实测暴露的问题

| # | 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | **MQ 消费端被注释，订单永远不落库** | `SeckillVoucherConsumer:26-30` 的 `@KafkaListener` 被 `/* */` 包住 | 用户拿到订单号却查不到订单 = 资损级 bug | 打开注解；或改回 `seckill.lua` 里注释掉的 Redis Stream 方案（`XADD stream.orders`），不依赖外部 Kafka |
| P0 | **`KafkaConfig` 三个 Bean 全被注释** | `KafkaConfig:42-78` | 没有自定义 `ConsumerFactory`，`application.yaml` 里 `JsonDeserializer` 配了但反序列化 `VoucherOrder` 时会拿不到类型 | 恢复 `consumerFactory` + `errorHandler` |
| P1 | **秒杀库存没有预热逻辑** | `VoucherServiceImpl:18` 导入了 `SECKILL_STOCK_KEY` 却没使用；`seckill.lua:17` 直接 `tonumber(redis.call('get', stockKey))` | 若 key 不存在，`tonumber(false)` 返回 nil，`nil <= 0` 会让 Lua 直接抛错，接口 500 | 加运营预热接口或 `@PostConstruct` 预热；Lua 里改成 `local stock = tonumber(redis.call('get', stockKey)) or 0` |
| P1 | **扣库存与落单没有事务** | `VoucherOrderServiceImpl` 的 `seckillVoucher` / `createVoucherOrder` 都没有 `@Transactional` | 第 6 步成功、第 7 步 `save()` 失败时，库存已经扣了但订单没生成，Redis 侧却已 `sadd`，永久丢单 | 给 `createVoucherOrder` 加 `@Transactional`；或引入对账/补偿任务 |
| P1 | **秒杀券有效期形同虚设** | `tb_seckill_voucher.end_time = 2025-06-09`，当前 2026-09-28，仍可下单 | 过期券仍能被抢 | 在 Lua 或服务层校验 `begin_time/end_time` |
| P2 | **`kafkaTemplate.send` 无回调、无降级** | `VoucherOrderServiceImpl:80` 未处理返回的 `CompletableFuture` | broker 挂了会阻塞到 `max.block.ms`（默认 60 秒），接口假死 | `.addCallback()` 记录失败；配置 `max.block.ms`；失败时同步兜底落库 |
| P2 | **上传目录硬编码** | `SystemConstants:4` = `D:\lesson\nginx-1.18.0\...` | 换机器上传功能直接不可用 | 改为配置项 |

## 附：一句话记忆版

> 这个项目的**骨架是 CRUD**，**灵魂是秒杀**。所有 Redis 的奇技淫巧（Lua、ZSet、BitMap、GEO、Set 交集、Hash token）都挂在一个"本地生活"的业务皮上；而秒杀这条链路的技术选型（先 Redis 抢资格、再异步落库）是标准的"削峰填谷"思路 —— **只是这个版本的 MQ 只写了生产端，消费端被注释了。**
